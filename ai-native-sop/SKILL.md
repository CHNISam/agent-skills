# AI Native 软件工程 SOP（第一性原理版）

## 为什么需要这个 SOP

AI Agent 大量参与开发后，瓶颈不再是"写代码的速度"，而是"人确认方向与验证结果的速度"。人如果逐行审查代码，就退化为低速代码检查器。本 SOP 的目标是：用最小必要流程控制软件变化，让需求、实现、验证、维护形成可靠闭环，使人只做三件事——定义目标、判断业务正确性、判断重大风险。

## 核心分工（所有步骤的基础）

**人负责：**
- 定义目标状态
- 判断业务正确性
- 判断重大风险

**Agent 负责：**
- 探索实现方案
- 编写代码
- 编写测试
- 调试修改

执行任何任务时，先按此分工规划交互点：只在"目标、验证方案、重大风险"处请求人工介入，其余环节自主完成。

## 第一性原理

1. **软件的目的**：软件不是生产代码，而是让机器按照人的意图改变现实状态。
   `现实状态 A → 软件规则 → 现实状态 B`
2. **质量的核心问题**：系统实际结果可能偏离期望结果。因此需要：明确什么叫正确 → 验证是否正确 → 发现偏差后修正。
3. 所有软件工程实践（Spec、Test、Architecture、CI 等）都只是核心循环的实现手段，而不是流程本身。不要为流程而流程。

## 标准流程

### Step 1：定义目标状态

回答：系统最终应该变成什么样？输出三项：
- 成功状态
- 失败状态
- 必要约束

描述的是可观察的系统终态，不是修改动作。

**示例：**
- 错误：「修复资讯没有封面」（这是任务描述，不是目标状态）
- 正确：「用户打开资讯列表时，每条资讯均展示正确封面」（这是可验证的终态）

### Step 2：判断变化风险

问题：这个修改是否改变系统未来行为规则？

| 低风险 | 高风险 |
|---|---|
| UI 调整 | 数据模型变化 |
| 文案修改 | API 契约变化 |
| 已有字段展示 | 权限变化 |
| 普通缺陷修复 | 核心流程变化 |

高风险变化需要额外的设计环节（先设计、再实现），并在请求人工介入时明确指出风险类别。

### Step 3：生成验证方案

不要默认假设人工编写测试。由 Agent 根据目标状态提出：
- 如何证明成功
- 测试覆盖范围
- 可能风险

请人工重点检查两点：
1. 验证方案是否验证了真实目标（而不是验证了实现细节）
2. 是否遗漏关键风险

不请人工检查测试代码实现细节。

### Step 4：Agent 实现

输入：目标状态 + 验证方案 + 代码库。

Agent 自主完成：
- 修改代码
- 添加测试
- 运行验证
- 修复问题

此阶段无需逐步请示。

### Step 5：验证

判断标准只有一个：实际系统状态是否符合目标状态。

验证重点不是代码长什么样，而是结果对不对。

### Step 6：错误沉淀

每次问题发生后追问：**为什么系统没有提前阻止这个问题？**

如果缺少规则，则补充以下之一：
- 测试保护（回归测试）
- 自动检查（lint / CI / 类型检查）
- 工程规则（写入 AGENTS.md / 本技能的沉淀区）

目标：第一次靠发现修复，第二次靠系统阻止。

### Step 7：复杂度控制

长期检查：这个变化是否增加未来修改成本？

关注四类信号：
- 重复逻辑
- 模块耦合
- 数据混乱
- 无法理解的代码

## 人工审查原则

必须人工关注：
1. 目标状态是否正确
2. 验证方案是否代表真实需求
3. 是否存在重大架构风险

通常无需人工逐行审查：
- 普通实现代码
- 测试代码细节
- Agent 执行步骤

## 执行清单（每次任务开始时过一遍）

1. 目标状态是什么？（成功/失败/约束）
2. 风险等级？（低/高；高则先设计）
3. 验证方案是否证明真实目标？
4. 实现后是否以"结果"而非"代码"完成验收？
5. 出错后是否有新的规则需要沉淀？
6. 本次变化是否引入了未来修改成本？

## 错误沉淀区

（本节用于跨会话积累经验：遇到新问题时，在此追加"场景 → 缺失的规则 → 已补充的保护措施"。仅沉淀跨项目通用的规则；项目特定的教训写入该项目自己的 AGENTS.md。）
