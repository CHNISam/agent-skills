# Git 分支、实验与集成管理规范（通用）

文档定位：一套项目无关的 Git 分支、实验、集成、归档与多人/多 Agent 协作规则，适用于高不确定性研发、产品原型、技术验证和常规团队开发。不绑定具体项目、语言、框架、平台或托管服务。本文用 `main` 代指"唯一长期集成基线"；若仓库实际使用 trunk、master 或其他名称，语义等价。目标不是套用 Git Flow、GitHub Flow 或 Trunk-Based Development 的完整教条，而是根据"为什么需要隔离"选择最小成本的机制。

## 1. 核心决策

- 默认只保留一个长期集成基线（本文记作 `main`）。
- `main` 不表示生产版本，也不要求每个提交都可发布；它表示"当前已经接受、已经集成、基本可运行，并适合作为下一轮工作的默认基线"。
- 当前不设永久 develop。只有未来真的出现"main = 正式发行线、develop = 下一版本长期集成线"这类两个长期真实状态时，才引入 develop。
- 普通协作、技术探索、产品探索和发布隔离，不用同一种分支生命周期强行解决。

## 2. 第一性原理

- 分支不是目的，而是隔离代码变化的一种机制。
- 是否需要隔离，先看原因，而不是先套命名规则。
- 主要隔离原因包括：多人或多 Agent 并行协作；尚未验证的产品或技术假设；有明确依赖关系的连续改动；正式发布或维护需要。
- 互斥假设不应机械合并。例如两套不能同时作为最终默认方案的架构或交互路线，可以并行探索，最终通常择一。
- 正交、可组合的能力应尽早验证组合效果。例如日志系统与存储实现、权限系统与界面改造可以分别开发，但最终需要在同一集成基线中验证。
- "接受实验结论"与"接受实验分支里的全部代码"是两件事。

## 3. main 的准入规则

- main 必须满足三个最低条件：当前方向已被接受；与现有基线可以共同工作；至少能够正常安装、构建，并通过项目约定的最小运行或 smoke check。
- main 不要求零临时代码，不要求生产级质量，也不要求每次都打 release tag。
- 如果一个改动尚未回答清楚"是否应该成为默认基线"，就不应仅因为做完了而进入 main。
- 如果一个实验结论成立，但分支里充满临时 hack、写死参数或验证性代码，应提取结论和可复用实现，从 main 重新做干净集成，而不是整条 merge。

## 4. 分支类型

- `main`：唯一长期集成基线。
- `change/*`：短命协作分支，可按团队习惯继续细分为 `feat/*`、`fix/*`、`refactor/*`。用于多人或多 Agent 并行、PR、Review、CI 等协作边界。完成后合并并删除。
- `exp/*`：所有"答案尚未确定"的探索统一使用此类分支，不强行区分 spike 与 prototype。实验目标可以是技术问题，也可以是产品体验问题。
- `release/*`：只有出现真实发布隔离需求时才创建，不作为原型阶段默认结构。
- 不为"看起来更专业"创建永久 develop、永久 feature 分支或没有退出条件的实验分支。

## 5. exp/* 的实验契约

每个 `exp/*` 必须至少写清楚四件事：

- **Question**：这条分支到底要回答什么未知问题。
- **Success Criterion**：什么事实出现时可以认为实验成立。
- **Relationship**：它与当前 main、其他实验是互斥、正交、依赖还是可运行时切换。
- **Disposition**：实验结束后准备怎么处理，通常是 accept、reject 或 continue。

`exp/*` 的代码可以非常快、非常脏，只要它能有效回答问题；因此"实验成功"不等于"整条实验分支应该 merge"。

## 6. 是否从 main 分叉

- 默认从 main 创建新分支。
- 只有当新工作明确依赖一个尚未进入 main 的实验时，才从对应实验分支继续分叉。
- 依赖式分叉必须是有意识的，不允许因为"当前正好在这个分支"就顺手继续叠加无关变化。
- 有依赖关系但希望保持 Review 粒度时，可使用 stacked PR / stacked branch 思路。

## 7. 互斥、正交与依赖

- **互斥**：两个方向不能同时成为同一个最终默认答案，例如两套替代性架构、渲染方案或交互范式。允许并行到足够做决定，最终择一；失败方向归档后删除活跃分支。
- **正交**：两个变化解决不同维度并且可以共存，例如可观测性与数据库迁移、权限控制与前端重构。可以独立协作，但应尽早组合到集成环境验证整体行为。
- **依赖**：后一个实验只有在前一个实验成立时才有意义。允许从前一个实验分支继续分叉，但必须明确依赖关系。
- **可切换**：两套实现可以暂时共存在同一代码库并运行时选择时，可优先考虑 Feature Flag 或 Branch by Abstraction，而不是长期维护两个巨大分支。

## 8. Feature Flag 的使用边界

- Feature Flag 用于"代码可以一起进入同一基线，但行为需要暂时开关"的场景。
- 适合：新旧实现切换、算法或服务版本开关、灰度发布、A/B 比较，以及可同时存在但暂不希望默认启用的能力。
- 不适合：为了追求 Trunk-Based 的形式，把两套根本互斥、长期并存成本很高的产品或架构路线都永久塞在同一份代码里。
- 所有 flag 都有 carrying cost，会增加条件逻辑、测试组合和认知负担，因此必须有删除条件和负责人。

## 9. 大型技术替换

- 对于旧实现到新实现的大型迁移，如果二者可以通过共同接口共存，优先考虑 Branch by Abstraction。
- 典型流程：先建立稳定抽象接口；在短命分支开发新实现；尽早合回 main；用 flag 或配置在新旧实现之间切换；验证新实现；删除旧实现、旧 flag 和迁移代码。
- 如果无法合理共存，或者探索本身可能被整体否决，则使用 `exp/*` 隔离更合适。

## 10. 多人和多 Agent 协作

- "单一长期 main"不等于"所有人直接向 main 写代码"。
- 多人或多 Agent 并行时，一项独立工作应有自己的短命 branch，并通过 PR、Review、CI 或等价检查进入 main。
- 并行任务较多时，建议使用 git worktree：一个 Agent / 一个并行任务对应一个 branch + 一个独立 working tree，避免频繁 checkout、stash 和文件互相污染。
- 协作分支的价值主要是并行工作空间、评审边界和集成边界，而不是产品实验本身。

## 11. 实验结束与归档

- **Reject**：保存可追溯墓碑后删除活跃分支。推荐 annotated tag + 简短 decision note，不依赖裸 commit hash。
- **Accept 且代码干净**：通过正常集成流程进入 main，再删除实验分支。
- **Accept 但代码很脏**：保留实验结论，从 main 重建或 cherry-pick/提取真正需要的部分；不要把"产品判断成立"等同于"原型实现全部值得保留"。
- **Continue**：只有仍存在明确未知问题时才继续，不允许无限期保留"以后可能有用"的分支。

## 12. Tag 与历史恢复

- Branch 是会移动的工作指针，Tag 更适合给已结束实验留下稳定名字。
- 失败但有参考价值的探索可使用类似 `archive/exp-storage-v2` 或 `archive/exp-renderer-b` 的 annotated tag，并在说明中记录为什么接受或放弃。
- Tag 的目的不是维护旧路线，而是让以后能低成本恢复历史资产、实现和决策上下文。

## 13. 推荐工作流

- 正常小改动：`main → change/* → PR/检查 → main → delete`。
- 技术或产品未知：`main → exp/* → 得到结论 → accept/reject/continue`。
- 实验成功且实现可复用：`exp/* → Review/清理 → main`。
- 实验成功但实现不可直接复用：`exp/* → 记录结论 → 从 main 干净实现 → main`。
- 互斥路线：`main → exp/A 与 exp/B 并行 → 决策 → 选中路线进入新基线，另一条归档`。
- 大型兼容替换：短命分支建立 abstraction → main 中并存新旧实现 → flag 切换 → 删除旧实现。

## 14. 明确的反模式

- 不要因为熟悉 Git Flow 就默认创建 develop。
- 不要把每一个 bug、UI 调整或素材变更都包装成长期实验。
- 不要把所有实验都强行 Feature Flag 化。
- 不要让 exp/* 没有明确问题和退出条件。
- 不要因为实验方向被认可就无条件 merge 整条原型分支。
- 不要从随机当前分支继续叠加无关工作。
- 不要让 main 变成"什么都能进"的垃圾场，也不要把它定义成原型阶段根本不存在的"生产稳定线"。

## 15. 面向未来 Agent Skill 的规则接口

- Agent 在创建 branch 前应先回答：为什么需要隔离；这是协作、实验、依赖还是发布；默认起点是否为 main；是否与其他实验互斥、正交、依赖或可切换；退出条件是什么。
- Agent 在合并前应检查：结论是否已被接受；main 是否仍能基本运行；实验实现是否值得直接进入 main；是否需要先清理、重建、拆分或只提取部分提交；是否应删除 branch、flag 或旧实现。
- Agent 在结束实验时应自动生成或更新 decision note，并在需要保留历史时创建 archive tag。
- 这些判断比固定的"feature branch 必须几天内合并"更重要；时间只是风险信号，不是产品探索的唯一规则。

## 16. 决策优先级

1. 第一优先：保护决策可逆性，避免探索 A 被探索 B 覆盖后只能整体回滚仓库状态。
2. 第二优先：维持一个可作为默认起点的 main，避免每次新工作都先猜"现在应该从哪个历史状态开始"。
3. 第三优先：降低并行协作冲突，让人和 Agent 的工作可独立 Review 和集成。
4. 第四优先：限制长期分支、Feature Flags 和旧实现造成的认知成本。
5. 第五优先：只有真实需求出现时才增加 release/develop 等额外结构。

## 17. 参考实践

- GitHub Flow / Pull Requests：单一默认分支、短命分支、PR Review 与合并。https://docs.github.com/en/get-started/using-github/github-flow
- Trunk-Based Development：短命 change branch、尽早集成、主线不应长期损坏。https://trunkbaseddevelopment.com/short-lived-feature-branches/
- Feature Toggles（Martin Fowler）：用运行时开关解耦部署与功能启用，同时警惕 carrying cost。https://martinfowler.com/articles/feature-toggles.html
- Branch by Abstraction（Martin Fowler）：大型实现替换时让新旧实现暂时共存，避免长期巨型分支。https://martinfowler.com/bliki/BranchByAbstraction.html
- Git worktree：同一仓库同时检出多个 working tree，适合多人或多 Agent 并行。https://git-scm.com/docs/git-worktree
- Agile Spike：用最小实验降低技术未知；其核心价值是获得知识，而不是保留实验代码。https://www.jamesshore.com/Agile-Book/spike_solutions.html

## 18. 当前规范的核心一句话

默认只有一个长期集成基线（本文记作 main）；其他机制按"为什么需要隔离"选择。实验统一用 `exp/*`，先回答未知问题，再决定是否、如何把学习结果和代码进入 main。
